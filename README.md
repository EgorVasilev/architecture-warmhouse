### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах

### 2. Анализ архитектуры монолитного приложения

#### 2.1 Определение списка ключевых архитектурных характеристик
Исходя из большого количества возможных архитектурных характеристик, выявлены ключевые для To-Be архитектурного решения, которые далее можно сравнить с As-Is решением

Явные архитектурные характеристики на основе задания:
- Usability (Сложность системы для конечного пользователя):
	- Система дружелюбна для польователя, он может установить новое устройство сам и без обязательного участия специалиста по подключению
- Extensibility (Расширяемость функциональности):
	- Требуется возможность подключения новых типов устройств в будущем
- Configurability (Гибкость конфигурации для конечного пользователя):
	- Нужно предоставить возможность создания произвольных сценариев для управления умными устройствами для конечных пользователей

Неявные архитектурные характеристики:
- Reliability/Safety (Отказоустойчивость):
	- Нельзя допустить чтобы некорректная работа устройств повредила здоровью или имуществу пользователя
	- Беспрепятственный переход к ручному управлению домом, если система управления устройствами испытывает неполадки
- Privacy (Способность обеспечение приватность):
	- Наличие систем видеонаблюджения требует соблюдение юридических и этических норм
- Legal (Юридические требования):
	- Система может подпадать под ряд важных юридических требований, например:
		- Статья 23 Конституции РФ (Неприкосновенность частной жизни)
		- Федеральный закон "О персональных данных"
		- Стандарт ГОСТ Р 71868-2024 «Системы киберфизические. Умный дом. Классы многоквартирных домов. Часть 1. Требования к классам»
- Authentication:
	- Доступ к системе только для зарегестрированных жильцов дома		

Исходя из потребностей бизнеса в
- Расширении сферы деятельности
	- Extensibility
- Выполнении тендера в срок и в рамках бюджета
	- Feasibility (Выполнимость)
- Обеспечении стабильного качества как SaaS
	- Usability
	- Authentication
	- Privacy

### **4. Проблемы монолитного решения**

Проблемы в контексте проекта:  
1. Расширяемость функционала (Extensibility): подключить новые типы устройств без переусложнения кода
2. В перспективе - масштабируемость (Scalability): выше цена поддержки большего числа домов, однако, на данный момент нет количественного прогноза о росте нагрузки

Преимущества в контексте проекта:
1. Проще в реализации и отладке - повышает выполнимость (Feasibility / Simplicity)
2. Дешевле
	- менее требователен к DevOps навыкам и ресурсам, техническим навыкам команды в целом
	- ниже операционные расходы на начальных этапах

Переход от монолита к микросервисам предложил бы делать через модульный монолит с упором на абстрактное взаимодействия между модулями (например, используя паттерн Proxy). Это могло бы снизить риски со сложностью реализации, но подготовить систему к постепенной эволюции в микросервисную по мере роста нагрузки.

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия использовать REST API. По возможности, реализация должна учитывать необходимый уровень абстракций, удешевляющих вероятный переход на иные способы/протоколы. Например, MQTT - характерный протокол для IoT-систем, AMQP как популярный протоколы для распределённых систем и событийный подход в целом. Высока вероятность перехода с REST на указанные альтернативы.

На начальном этапе выбор REST API обусловлен:
1. Минимизация технической сложность: команда имеет опыт работы с REST API
2. Относительно прост в тестировании и отладке: снижение Time-to-Market, актуально для MVP стадии и соблюдению сроков тендера

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
